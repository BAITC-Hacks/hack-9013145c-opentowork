# Как запустить проект

Инструкция для человека, который видит проект впервые. Ключи API, внешние
аккаунты и ручная загрузка данных не нужны: всё, что требуется для работы,
лежит в репозитории или создаётся автоматически при первом старте.

Кратко:

```bash
git clone https://github.com/BAITC-Hacks/hack-9013145c-opentowork.git
cd hack-9013145c-opentowork
cp .env.example .env              # Windows: copy .env.example .env
docker compose up -d --build
```

Откройте http://localhost:3000, войдите как `demo@demo.kz` / `demo1234`.

Ниже — подробности по каждому шагу.

---

## 1. Что нужно установить

| Что | Зачем | Обязательно |
|---|---|---|
| Docker + Docker Compose v2 (на macOS/Windows — Docker Desktop) | весь стек поднимается в контейнерах | да |
| Git | скачать репозиторий | да |
| Python 3 (любой, без пакетов) | запустить сквозную проверку `scripts/smoke_test.py` | для проверки |
| `make` | короткие команды; на Windows не работает — есть аналоги на `docker compose` | нет |
| Python 3.12+ и Node.js 22 | только для запуска без Docker (раздел 8) | нет |

Ресурсы: Docker Desktop с 4 ГБ памяти или больше. Первая сборка скачивает образы
и зависимости, поэтому нужен интернет.

Порты, которые должны быть свободны:

| Порт | Сервис |
|---|---|
| 3000 | веб-интерфейс (nginx) |
| 8000 | API (FastAPI) |
| 5432 | PostgreSQL 16 + pgvector |
| 6379 | Redis |
| 9000, 9001 | MinIO (S3-хранилище) и его консоль |
| 9090, 3001 | Prometheus и Grafana — только если включён мониторинг |

---

## 2. Настройка `.env`

```bash
cp .env.example .env
```

Больше ничего менять не нужно. Значения по умолчанию рассчитаны на локальный стенд:

- `LLM_MODE=mock` — встроенный провайдер вместо внешней LLM и локальные эмбеддинги,
  интернет и ключи не нужны;
- `SEED_ON_START=true` — при старте создаются демо-пользователь и демо-данные;
- `APP_ENV=dev` — разрешены секреты по умолчанию (при `APP_ENV=prod` приложение
  с ними откажется стартовать — это защита, а не поломка).

Файл `.env` не хранится в git, `.env.example` — хранится.

---

## 3. Запуск

```bash
docker compose up -d --build
```

Что происходит:

1. Собирается образ бэкенда. На отдельной стадии сборки **обучается ML-модель
   прогноза ВЭС** (`python -m windcast train`) — файл модели не хранится в git
   и всегда соответствует версиям библиотек образа. Это самая долгая часть первой
   сборки, порядка нескольких минут.
2. Собирается фронтенд (React + Vite) и упаковывается в nginx.
3. Поднимаются PostgreSQL, Redis, MinIO.
4. Контейнер `api` ждёт базу, применяет миграции и создаёт демо-данные.
5. Стартуют `api`, два воркера фоновых задач и `frontend`.

Стек готов, когда:

```bash
docker compose ps        # у api, worker, frontend — статус healthy
curl http://localhost:8000/health    # {"status":"ok",...}
```

Если `api` долго не становится `healthy` — смотрите `docker compose logs -f api`.

С `make` то же самое: `make up`.

## 4. Адреса и учётные данные

| Что | Адрес | Логин / пароль |
|---|---|---|
| **Веб-интерфейс** | http://localhost:3000 | `demo@demo.kz` / `demo1234` |
| API, Swagger | http://localhost:8000/docs | тот же демо-пользователь |
| Health / Ready | http://localhost:8000/health, http://localhost:8000/ready | — |
| Метрики Prometheus | http://localhost:8000/metrics | — |
| Консоль MinIO | http://localhost:9001 | `minioadmin` / `minioadmin` |
| PostgreSQL | `localhost:5432`, база `app` | `app` / `app` |
| Grafana (по желанию) | http://localhost:3001 | `admin` / `admin` |

Демо-пользователь имеет роль `EXPERT`, не `ADMIN`: он наполняет базу знаний,
но не видит данные других пользователей.

Мониторинг включается отдельно:

```bash
docker compose --profile observability up -d
```

## 5. Данные: что откуда берётся

Скачивать ничего не нужно — все данные лежат в репозитории.

| Данные | Где лежат | Откуда | Для чего |
|---|---|---|---|
| SCADA двух турбин ВЭС Нурлы, 10-минутные замеры с 11.03.2023 по 31.01.2026 | `datasets/turbine_1.csv`, `datasets/turbine_2.csv` | датасет организатора кейса | обучение модели, история турбин, бэктест |
| Архивные **прогнозы** погоды 7 моделей (ECMWF IFS, ECMWF AIFS, ICON, GFS, UKMO, GEM, CMA) | `artifacts/weather/*.parquet` | Open-Meteo Historical Forecast API, уже скачано | признаки модели; сеть не нужна |
| Кривая мощности турбины | `artifacts/models/power_curve.json` | построена по SCADA | базовая модель и сценарий «что если» |
| Файл обученной модели | `artifacts/models/forecaster.pkl` | **создаётся при сборке Docker**, в git его нет | прогноз |
| Прогнозы тестового периода 31.01–27.02.2026 | `artifacts/forecasts/` | результат `python -m windcast test-period` | экран станции без интернета |
| Результаты бэктеста 02.2025–01.2026 | `artifacts/reports/` | результат `python -m windcast backtest` | вкладка «Точность прогноза» |
| Объяснения прогнозов | `artifacts/explain/` | результат расчёта TreeSHAP | экран «Почему прогноз такой» |
| Черновики заявок в РФЦ | `artifacts/bids/` | результат `python -m windcast bids` | вкладка «Заявка РФЦ» |
| Справочник ВЭС Казахстана | `app/wind/data/` | OpenStreetMap; реестр Минэнерго РК на январь 2026 (карта ВИЭ QazaqGreen) | карта и раздел «Прогнозы» |
| СЭС и крыши трёх городов | `app/solar/data/` | OpenStreetMap | солнечные станции и «Панели на крышах» |
| Демо-пользователь, документы базы знаний | создаются в PostgreSQL при старте | `app/scripts/seed.py` | вход и AI-платформа |

Формат SCADA: `ID, Статистическое время, Средняя скорость ветра (m/s),
Нормализованная активная мощность, Средняя температура окружающей среды (°C)`.
Мощность — в долях номинала, так же выдаётся и прогноз.

Главный результат ML-части: `artifacts/forecasts/test_period_forecast.csv` —
28 выпусков (31.01…27.02.2026, каждый в 00:00 UTC) × 48 часов, колонки P10/P50/P90
и прогноз по каждой турбине.

### Что работает без интернета, а что — нет

| Работает офлайн | Нужен интернет у контейнера `api` или у браузера |
|---|---|
| Прогноз Нурлы за тестовый период, 3D-сцена, история турбин | «Сейчас · живой прогноз» (Open-Meteo) |
| «Точность прогноза», «Почему прогноз такой» для тестового периода | раздел «Прогнозы» по всем ВЭС |
| Агент, Copilot, AI-платформа в режиме `mock` | солнечные станции, «Новая площадка» |
| «Заявка РФЦ» с выгрузкой PDF/DOCX/CSV/JSON | подложка карты городов (OpenFreeMap) — расчёт крыш от неё не зависит |
| Расчёт панелей на крышах | |

Без сети эти разделы отвечают понятной ошибкой («погодный сервис недоступен»),
а не падают.

У всех станций, кроме Нурлы, прогноз строится по ветру Open-Meteo и кривой
мощности Нурлы, а не ML-моделью. Истории выработки у этих станций нет, и в
интерфейсе это подписано.

## 6. Как убедиться, что всё работает

### Автоматически

```bash
python3 scripts/smoke_test.py          # или: make smoke
```

Скрипт проходит весь основной путь: вход, AI-ответ и кэш, фоновую задачу,
прогноз ВЭС, сценарий «что если», Copilot и историю SCADA. По каждой проверке
он печатает `PASS` или `FAIL`, а в конце — `Все проверки пройдены — проект готов к сдаче.`

Проверка развёрнутого сервера: `python3 scripts/smoke_test.py --base http://<адрес>:8000`.

### Вручную, за 3 минуты

1. http://localhost:3000 → войти демо-пользователем.
2. **Ветровая энергия** → **ВЭС Нурлы** (или сразу http://localhost:3000/#/forecast/wind/nurly).
3. «Дата прогноза» → **07.02.2026**: график P10–P90 и 3D-сцена станции.
4. Переключить **24 ч / 48 ч**.
5. Вкладки **«Точность прогноза»**, **«Как считается»** (агент и Copilot), **«Заявка РФЦ»**.
6. Под графиком — **«Объяснить прогноз →»**.

### Через API

```bash
curl "http://localhost:8000/api/v1/forecast/latest?origin=2026-02-07"   # прогноз 48 ч
curl  http://localhost:8000/api/v1/metrics                              # метрики бэктеста
```

## 7. Остановка и сброс

```bash
docker compose down        # остановить, данные сохраняются
docker compose down -v     # остановить и удалить БД, кэш и файлы
```

Проверка «как на чистой машине»:

```bash
docker compose down -v && docker compose up -d --build && python3 scripts/smoke_test.py
# или: make reset
```

## 8. Запуск без Docker (для разработки)

Инфраструктура всё равно берётся из Docker, а API, модель и фронтенд работают
локально.

```bash
python3 -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -e ".[dev,ml]"

python -m windcast train                    # обучить модель (в git её нет)

docker compose up -d postgres redis minio   # только инфраструктура
```

В `.env` замените хосты на `localhost`: `@postgres:` → `@localhost:` в `DATABASE_URL`,
`redis://redis` → `redis://localhost` в `REDIS_URL`, `http://minio` → `http://localhost`
в `S3_ENDPOINT`. Затем:

```bash
alembic upgrade head                        # миграции
python -m app.scripts.seed                  # демо-пользователь и данные
WINDCAST_LIVE=1 uvicorn app.main:app --reload   # API на :8000

cd frontend && npm install && npm run dev   # интерфейс на http://localhost:5173
```

Воркер фоновых задач: `python -m app.workers.main`. На Windows локально он не
стартует, поднимайте его через Docker.

### Воспроизвести ML-результаты с нуля

Всё работает офлайн на данных из репозитория:

```bash
python -m windcast quality        # качество данных турбин
python -m windcast backtest       # бэктест 02.2025–01.2026, 365 выпусков (несколько минут)
python -m windcast train          # итоговая модель на данных до 31.01.2026 00:00 UTC
python -m windcast test-period    # прогноз на тестовый период 31.01–27.02.2026
python -m windcast bids           # черновики заявок в РФЦ
python -m windcast weather        # необязательно: заново скачать архив погоды (нужен интернет)
```

### Тесты

```bash
pytest -q && ruff check .         # или: make test
make test-docker                  # то же внутри контейнера — работает на Windows
make test-integration             # проверки доступа, нужен поднятый стек
```

## 9. Подключить настоящую LLM (необязательно)

В `.env`:

```
LLM_MODE=live
LLM_API_KEY=ваш_ключ
```

Затем выполните `docker compose up -d`. Пороги семантического кэша переключатся
на рабочие значения автоматически. Всё остальное работает так же, как в `mock`.

## 10. Если что-то не работает

| Симптом | Что сделать |
|---|---|
| `port is already allocated` | порт занят — остановите программу или поменяйте левую часть `ports:` в `docker-compose.yml` |
| `api` долго не `healthy` | первая сборка обучает модель и применяет миграции — `docker compose logs -f api` |
| Не входит `demo@demo.kz` | в `.env` должно быть `SEED_ON_START=true`; после правки — `docker compose down -v && docker compose up -d` |
| «Прогнозы» / живой прогноз — ошибка погодного сервиса | нет интернета у контейнера `api`; тестовый период работает офлайн |
| На экране крыш нет карты города | подложку карты браузер берёт из интернета; расчёт от неё не зависит |
| Ответ из кэша не появляется при повторном вопросе | кэш свой у каждого пользователя — спрашивайте из той же учётки |
| `429 Too Many Requests` | лимит 20 AI-запросов в минуту на пользователя (`RATE_LIMIT_AI` в `.env`) |
| `make` не работает (Windows) | используйте команды `docker compose` из этого файла |
| Нужно начать с чистого листа | `docker compose down -v && docker compose up -d --build` |

Подробнее об устройстве проекта — в [README.md](README.md).

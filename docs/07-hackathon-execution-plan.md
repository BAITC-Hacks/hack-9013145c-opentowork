## 7.2 Завтра: первые 30 минут после объявления кейса

Самое дорогое время. Не бросайтесь кодить.

**13:00–13:15 — Разбор кейса (вся команда):**
1. Кто пользователь и какую боль решаем? Одним предложением.
2. Какой **один** сценарий покажем жюри на демо? (end-to-end, от входа до результата)
3. Что в этом сценарии делает AI и почему без AI нельзя?
4. Что из ТЗ кейса обязательно (там могут быть свои критерии оценки — п. 5.5.1)?

**13:15–13:30 — Маппинг на каркас:**
1. `DOMAIN_ENTITY` → как называется в кейсе? Какие 3–5 полей критичны?
2. `CACHE_CONTEXT_FIELDS` → что делает два похожих запроса разными? (§2.3)
3. Доменные правила валидации → какие 1–2 проверки вставим в `domain_rules.validate()`?
4. База знаний для RAG → что туда положим? (ТЗ кейса, открытые данные, свои тексты)
5. Распределение ролей: бэкенд / AI-слой / фронтенд+демо.

Результат: коммит `docs/case-mapping.md` с ответами. Это **сразу же** ваш первый
почасовой артефакт прогресса (п. 5.4.8).

### Критические правила часов 4 и 5

- **17:00 — hard stop на новые фичи.** Всё, что не работает к 17:00, вырезается
  или прячется за фиче-флаг. Незакоммиченный сломанный код в 17:59 — потеря проекта.
- **Проверка «чистой машины»**: полностью снести состояние и подняться с нуля,
  как это сделает технический эксперт (п. 5.6.3–5.6.5):
  ```bash
  docker compose down -v && docker compose up -d && python3 scripts/smoke_test.py
  ```
  `scripts/smoke_test.py` проходит весь сценарий и печатает PASS/FAIL по пунктам.
  Если что-то красное — это важнее любой недоделанной фичи.
- **Видео-запись демо** (2–3 минуты, экран + голос). Если на Demo Day 29.09 упадёт
  интернет или сервис — вы показываете запись, а не оправдываетесь.
- **Seed-данные**: демо не должно требовать ручного заполнения БД. `SEED_ON_START=true`
  создаёт демо-пользователя (`demo@demo.kz / demo1234`), пару объектов и наполненную
  базу знаний. Логин/пароль — в README (это же закрывает п. 5.6.6: проверка без

## 7.6 Что говорить на Demo Day (структура на 100 баллов)

| Критерий | Баллы | Что показать |
|---|---|---|
| Ценность решения | 25 | Кто пользователь, какая боль, сколько это стоит сейчас. Цифры, даже оценочные |
| Результат и качество | 20 | Живое демо сквозного сценария. Не слайды — работающий продукт |
| Инновационность | 15 | Semantic cache + валидация выхода LLM доменными правилами. Покажите `meta.source: semantic_cache` и latency 62 мс против 2400 мс |
| Потенциал развития | 20 | Схема K8s, HPA, независимое масштабирование воркеров, «что дальше за 3 месяца» |
| Презентация и ответы | 20 | Репетиция. Один говорящий, один за ноутбуком. Заранее подготовьте ответы на «а если 10 000 пользователей?», «сколько стоит запрос?», «что если LLM ошибётся?» |

Три вопроса, которые задают почти всегда — ответы у вас уже заложены в архитектуру:

1. *«Что если LLM выдаст неверный ответ?»* → четыре слоя валидации, grounding по
   источникам, доменные правила, degraded-ответ вместо выдумки, флаг
   `needs_expert_review`.
2. *«Как это масштабируется?»* → stateless API + HPA 2→10, воркеры 1→20 по длине
   очереди, semantic cache снимает 30–45% нагрузки с LLM.
3. *«Сколько это стоит в проде?»* → метрика `ai_estimated_cost_usd_total`,
   экономия от кэша в процентах и в деньгах.

# Развёртываемость

Один и тот же код разворачивается тремя способами. Для каждого есть своя
команда, и каждый проверен запуском, кроме отдельно отмеченных мест:

| Уровень | Для чего | Команда | Статус |
|---|---|---|---|
| **Docker Compose** | ноутбук проверяющего, разработка | `make up` / `docker compose up -d` | проверено, основной путь по README |
| **Демо-сервер** | публичный стенд, автодеплой из `main` | пуш в `main` → GitHub Actions | работает, `http://89.126.192.240:3000` |
| **Kubernetes** | рост нагрузки, прод | `kubectl apply -k infra/k8s/` | локальный оверлей развёрнут; боевой набор проверен только `--dry-run=server` |

Подробности манифестов и граблей — в [05-deployment-and-kubernetes.md](05-deployment-and-kubernetes.md)
и [`context/06-kubernetes.md`](../context/06-kubernetes.md). Здесь — зачем это всё и
что на самом деле работает.

---

## 0. Что именно поднимается

Состав одинаковый: API, воркеры, фронтенд, Postgres с pgvector, Redis и MinIO.
Различается то, чем каждый компонент управляется, сколько у него копий и как он
доступен снаружи.

| Компонент | Docker Compose (`docker-compose.yml`) | Kubernetes, база (`infra/k8s/`) | Kubernetes, ноутбук (`infra/k8s-local/`) |
|---|---|---|---|
| **API** (FastAPI, `backend.Dockerfile`) | сервис `api`, 1 контейнер, порт `8000` наружу | Deployment `api`, 3 реплики, HPA 2→10, PDB, Service ClusterIP `:8000` | 1 реплика, HPA тот же, без PDB |
| **Воркер** (тот же образ, `python -m app.workers.main`) | сервис `worker`, 2 реплики (`--scale worker=N`), без портов | Deployment `worker`, 2 реплики, HPA 1→20, без Service | 1 реплика |
| **Миграции** | entrypoint контейнера `api` при старте | отдельный Job `db-migrate`, поды запускаются с `RUN_MIGRATIONS=false` | то же |
| **Сид-данные, демо-учётка** | при старте, если `SEED_ON_START=true` (так в `.env.example`) | не создаются: в ConfigMap `SEED_ON_START=false` | создаются: `SEED_ON_START=true` в оверлее |
| **Фронтенд** (React + nginx, `frontend.Dockerfile`) | сервис `frontend`, порт `3000` | Deployment `frontend`, 2 реплики, Service `:3000` | 1 реплика |
| **PostgreSQL 16 + pgvector** | контейнер `pgvector/pgvector:pg16`, том `pgdata`, порт `5432` наружу | StatefulSet, 1 реплика, PVC 20 Gi, headless Service | PVC 2 Gi |
| **Redis 7** (кэш + очередь) | контейнер, AOF, том `redisdata`, порт `6379` наружу | Deployment, 1 реплика, AOF, `maxmemory 512mb` + LRU, **без тома** | то же |
| **MinIO** (S3 для файлов) | контейнер, том `miniodata`, порты `9000`/`9001` | StatefulSet, 1 реплика, PVC 10 Gi | PVC 1 Gi |
| **Prometheus + Grafana** | только с `--profile observability`: `:9090`, Grafana на `:3001` с готовым дашбордом | не разворачиваются; у подов API есть аннотации `prometheus.io/*` для Prometheus кластера | нет |
| **Вход снаружи** | порты хоста: `3000` интерфейс, `8000` API | Ingress: `/api`, `/docs`, `/openapi.json`, `/health`, `/ready` → API, остальное → фронтенд; TLS | Ingress удалён, вход через `make k8s-forward` (port-forward `3000` и `8000`) |
| **Конфигурация** | `.env` (копия `.env.example`, `LLM_MODE=mock`) | ConfigMap `app-config` (`LLM_MODE=live`) + Secret `app-secrets` с ключом, секрет создаётся вручную | ConfigMap с `LLM_MODE=mock` и заведомо небоевой Secret из `secretGenerator` |
| **Образы** | собираются на месте (`build:`) | из registry `ghcr.io/OWNER/…`, тег подставляется | локально собранные, загружены в ноду (`make k8s-load`), `imagePullPolicy: Never` |

Демо-сервер — это тот же Docker Compose. Отличие одно: рядом лежит
`docker-compose.override.yml`, который открывает Postgres, Redis и MinIO только на
`127.0.0.1`. Наружу доступны только `:3000` и `:8000`.

Что стоит знать:

- **Redis в Kubernetes без тома.** AOF пишется в файловую систему контейнера, поэтому
  при перезапуске пода пропадают кэш и незабранные задачи из очереди. Для кэша это
  допустимо, для очереди — нет. В проде нужен managed Redis или PVC.
- **В базовом кластере нет сид-данных.** Демо-учётку в проде нужно создать вручную
  или включить `SEED_ON_START`.
- **В Compose порты БД, Redis и MinIO открыты наружу** — это удобно на ноутбуке.
  На сервере их закрывает override-файл.

## 1. Запуск без аккаунтов и ключей

Проект должен подниматься у постороннего человека по README (п. 5.4.16), без
личных аккаунтов (п. 5.6.6). Поэтому:

- `LLM_MODE=mock` по умолчанию: `MockProvider` + `HashingEmbedder`, сеть и ключи не нужны;
- `.env` создаётся из `.env.example` командой `make up`, если его нет;
- миграции применяются в entrypoint контейнера, демо-учётка и сид-данные создаются на старте;
- у Postgres и Redis есть healthcheck, и API ждёт их через `depends_on: service_healthy`,
  поэтому стек не падает на первом старте из-за порядка запуска.

```bash
cp .env.example .env
docker compose up -d
python3 scripts/smoke_test.py      # сквозная проверка, PASS/FAIL по пунктам
```

Последний прогон smoke на существующем локальном стенде дал 21/21 PASS (журнал —
[`context/00-state.md`](../context/00-state.md) §2). Чистая установка со сносом
томов (`make reset`) в тот раз не проверялась.

## 2. Один образ — несколько ролей

API, воркер и Job миграций запускаются из одного образа `backend.Dockerfile`,
отличается только команда запуска. Поэтому зависимости двух сервисов не могут
разъехаться, а собирать и хранить в registry нужно один образ вместо двух.
Фронтенд — отдельный образ: nginx раздаёт собранный React и проксирует `/api`
на бэкенд, так что baseURL не зашивается при сборке.

Образы собраны в несколько стадий и запускаются не от root (`USER app`, uid 1000).
Это же требование повторяют манифесты: `runAsNonRoot`, `drop: ["ALL"]`.

## 3. Почему Kubernetes, а не только Compose

Compose хватает для одной машины. Kubernetes понадобится, когда станций и
пользователей станет больше и одна машина перестанет справляться. Что он даёт
именно этому проекту:

**API и воркеры масштабируются отдельно.** Нагрузки у них разные. API отвечает на
короткие HTTP-запросы, а воркеры выполняют длинные задачи: AI-анализ и пересчёт
прогноза ВЭС. Поэтому у каждого свой Deployment и свой HPA:

| Компонент | Реплики | Масштабирование |
|---|---|---|
| API | 3 (HPA 2 → 10) | CPU 70 %, память 80 % |
| Воркер | 2 (HPA 1 → 20) | CPU 75 % |

Всплеск тяжёлых задач добавляет поды воркеров, но не API, а наплыв пользователей
добавляет поды API, но не воркеров. Очередь в Redis связывает их без прямых
вызовов: задачу ставит один под, забирает любой другой. В локальном кластере это
проверено: задачу создал под API, обработал под воркера.

**Обновление без простоя.** Rolling update с `maxUnavailable: 0` и `maxSurge: 1`:
старый под не гасится, пока новый не прошёл readiness. `preStop: sleep 5` даёт
балансировщику убрать под из ротации до остановки. PodDisruptionBudget
(`maxUnavailable: 1`) не даёт вывести из работы все реплики сразу при
обслуживании узла.

**Самовосстановление без каскадных отказов.** Пробы разделены:

- liveness `/health` проверяет только то, что процесс жив, и не трогает БД.
  Иначе кратковременная просадка базы перезапустила бы все поды разом;
- readiness `/ready` проверяет БД и Redis. Если они недоступны, под просто
  перестаёт получать трафик и не перезапускается;
- startup-проба даёт время на медленный старт, не мешая liveness;
- у воркера нет HTTP-порта, поэтому его liveness — свежесть heartbeat-файла
  `/tmp/worker_alive`, как и в healthcheck Compose.

**Миграции выполняются один раз.** Отдельный Job `db-migrate`, а не entrypoint
каждого пода: иначе три реплики API одновременно запустили бы `alembic upgrade head`
на одной базе. Поды приложения стартуют с `RUN_MIGRATIONS=false` и не получают
трафик, пока схемы нет: `/ready` отвечает 503.

**Секреты не попадают в git.** `secret.yaml` — шаблон со значениями `REPLACE_ME`, и
он намеренно не подключён к `kustomization.yaml`. Иначе в кластер можно было бы
выкатить общеизвестный `JWT_SECRET`. Боевой секрет создаётся отдельной командой.

## 4. Одна база манифестов, разные окружения

```
infra/k8s/          базовый набор: 3 реплики API, Ingress + TLS, образы из registry
infra/k8s-local/    оверлей для ноутбука: локальные образы, 1 реплика,
                    LLM_MODE=mock, без Ingress и PDB, небоевой секрет
```

Оверлей Kustomize меняет только то, что отличается между окружениями. Манифесты
не копируются, поэтому прод и локальный стенд не разъезжаются.

```bash
make k8s-up      # собрать образы, загрузить в ноду, применить оверлей
make k8s-status  # поды, HPA, потребление
make k8s-smoke   # сквозная проверка через port-forward
make k8s-down    # снести namespace
```

## 5. CI/CD

- **`ci.yml`** запускается на каждый пуш: `ruff` и `pytest` в режиме mock.
  На `main` после этого идёт деплой на демо-сервер: rsync кода,
  `docker compose up -d --build`, затем ожидание `/health` у API и 200 от фронтенда.
  Если стенд не поднялся за 2 минуты, деплой падает и печатает логи API.
  Ключ хоста закреплён в workflow, а не берётся через `ssh-keyscan`.
- **`checks.yml`** запускается на PR и вручную: интеграционные тесты изоляции
  данных на настоящих Postgres и Redis, поиск секретов (gitleaks), аудит
  зависимостей (pip-audit), статический анализ (bandit).

Деплой в Kubernetes из CI не настроен. В `kustomization.yaml` описано, как CI
подставляет тег образа (`kustomize edit set image … :$GITHUB_SHA`), но такого шага
в workflow нет.

## 6. Что проверено, а что нет

| Проверено запуском (23.09.2026) | Как |
|---|---|
| Compose-стек поднимается и проходит сквозную проверку | `smoke_test.py` — 21/21 PASS на локальном стенде |
| Базовые манифесты валидны против настоящего API-сервера | `kubectl apply --dry-run=server -k infra/k8s/` |
| Локальный кластер разворачивается с нуля | `kubectl apply -k infra/k8s-local/`, Job миграций → `Completed` |
| Сценарий работает в кластере | `smoke_test.py` через port-forward — 15/15 PASS |
| HPA реально масштабирует | при пониженном пороге API вырос с 2 до 4 реплик за 30 секунд |

| Не проверено | Почему |
|---|---|
| `infra/k8s/` в боевом кластере | нужны registry, домен и настоящие секреты |
| Ingress и TLS (cert-manager) | нужны ingress-контроллер и публичный домен |
| Отказоустойчивость БД | Postgres в кластере — одна реплика StatefulSet; для прода — managed-сервис |
| Пропускная способность | нагрузочного теста не было, цифр RPS нет |
| Масштабирование воркеров по длине очереди | HPA воркеров работает по CPU; вариант на KEDA описан в `hpa.yaml` комментарием, но не подключён |

Последний пункт важен для прогноза ВЭС. Пока воркер ждёт ответа погодного API
или LLM, CPU почти не загружен, и HPA по CPU может не заметить растущую очередь.
Правильный сигнал — длина очереди. Это следующий шаг, но пока он не сделан.

## 7. Путь в прод

1. Собрать образы и запушить в registry (`ghcr.io/…/hackalem-api`, `…-frontend`).
2. Postgres и Redis заменить на managed-сервисы: бэкапы, репликация и failover
   входят в услугу. `stateful-services.yaml` остаётся для стейджа.
3. Создать `app-secrets` из хранилища секретов, задать `LLM_MODE=live` и ключ.
4. `kubectl apply -k infra/k8s/`, домен — в `ingress.yaml`.
5. Добавить в CI шаг `kustomize edit set image` и `kubectl apply`.
6. Подключить KEDA, чтобы воркеры масштабировались по длине очереди.

# Контекст проекта

Хакатон HackAlem AI, 23.09.2026, команда OpenToWork. Репозиторий выдан организатором
через edu.astanahub.com — это единственное место, где ведётся разработка (п. 5.4.9).

Домен-агностичная AI-платформа: инфраструктура готова и проверена, доменная логика
подставляется после объявления кейса в 13:00.

## ЧИТАТЬ ПЕРВЫМ

**`context/00-state.md` — живой журнал состояния проекта.** Там текущая правда:
что уже сделано, что проверено запуском и когда, что делать дальше, какие ловушки
есть на демо. Начинать любую работу с него, а не с чтения кода.

## Правило работы с контекстом — обязательное

**После каждого изменения в проекте обновлять `context/00-state.md`.**
Не в конце дня, не «когда будет время» — сразу, в том же заходе, что и правка.

Что именно обновлять:

| Изменил | Обнови в `00-state.md` |
|---|---|
| Поведение или конфигурацию | §4 «Ловушки» — если меняется то, что видно на демо |
| Выполнил пункт плана | §5 — отметить галочкой |
| Любую правку кода | §8 «Журнал изменений» — строка сверху: что, зачем, чем проверено |
| Прогнал проверки | §2 — цифры и дата |
| Нашёл новый риск | §6 |

Остальные файлы `context/` описывают устройство и меняются редко — их трогать
только если менялась сама структура проекта:

| Изменил | Обнови |
|---|---|
| Добавил или переименовал файл | `context/01-map.md` |
| Добавил фичу или эндпоинт | `context/02-features.md` |
| Появился новый типовой приём | `context/03-recipes.md` |
| Наступил на грабли и починил | `context/04-troubleshooting.md` |
| Изменил путь запроса | `context/05-request-flow.md` |
| Тронул манифесты | `context/06-kubernetes.md` |

**Два запрета, из-за которых этот раздел и появился:**

1. **Не писать в документацию то, чего код не делает.** Внешнее ревью нашло три
   десятка мест, где комментарий обещал больше, чем работало: «at-least-once» без
   ретраев, «логи без секретов» при невызываемом `redact()`. Если свойство не
   проверено запуском — так и писать, а не утверждать.
2. **Не называть непроверенные цифры как измеренные.** Если написано «15/15
   проверок» — значит `make smoke` прогонялся и дал этот результат.

## Жёсткие ограничения — проверять перед действиями

- **Коммиты только после 13:00 23.09.2026.** До старта соревновательной части ничего
  не коммитить и не пушить, даже если работа готова. Файлы остаются в рабочем дереве.
- **Каждый час нужен коммит с реальным прогрессом** (п. 5.4.8). Отсутствие — основание
  для дисквалификации (п. 5.9.2). Коммиты разбивать по смыслу, а не сваливать в один.
- **Проект должен подниматься по README у постороннего** (п. 5.4.16). Если не
  запустился — команда не допускается, пояснения не принимаются.
- **Проверка без личных аккаунтов** (п. 5.6.6). Поэтому `LLM_MODE=mock` по умолчанию,
  демо-учётка и сид-данные создаются автоматически.
- Соревновательная часть 13:00–18:00, итоговая версия фиксируется на 18:00.

## Команды

```bash
make up          # поднять стек
make smoke       # сквозная проверка всего пути (PASS/FAIL по пунктам)
make test        # pytest + ruff
make reset       # снести тома и поднять заново — проверка «чистой машины»
make logs        # логи api и воркеров
```

Без make: `docker compose up -d`, `python3 scripts/smoke_test.py`, `.venv/bin/pytest -q`.

На Windows `make` и `.venv/bin/...` не работают — только `docker compose` и
`make test-docker` (тесты и линтер внутри контейнера). Воркер локально на Windows
тоже не стартует (`add_signal_handler` не поддерживается), поднимать через Docker.

## Архитектура

Модульный монолит на FastAPI + асинхронные воркеры. PostgreSQL 16 + pgvector, Redis,
S3-совместимое хранилище.

- **Что сейчас правда** — `context/00-state.md` (живой журнал, читать первым).
- **Где что лежит и как что-то сделать** — `context/` (навигация в `context/README.md`).
- **Почему сделано именно так** — `docs/01`…`docs/07`, начинать с `docs/00-index.md`.

Путь AI-запроса: `guard → exact cache (Redis) → embedding → semantic cache (pgvector)
→ RAG → LLM → валидация с ретраем → degraded-ответ при неудаче → запись в кэш`.

Фронтенд (React + Vite) раздаётся nginx на :3000 и проксирует `/api` на бэкенд,
поэтому ходит по относительному пути: ни CORS, ни зашитый при сборке baseURL не нужны.

## Что меняется под кейс, а что нет

Меняется: `app/domain/rules.py` (в первую очередь `RANGE_RULES` — таблица
допустимых диапазонов, движок проверки уже написан), `DomainEntity` в
`app/models.py`, `app/api/v1/entities.py`, `CACHE_CONTEXT_FIELDS` в `.env`,
промпты в `app/ai/prompts.py`, сид-документы в `app/scripts/seed.py`, поля
в `AIAnswer`, тексты и вкладки во `frontend/src/App.tsx`.

Не меняется: инфраструктура, auth, кэш, очередь, валидация, K8s, CI, `frontend/src/api.ts`
(кроме новых методов), плашка происхождения ответа.

## Конвенции

- Конфигурация только через `app/config.py` (pydantic-settings), никаких значений в коде.
- Ошибки — через классы из `app/errors.py`, наружу единый формат с `request_id`.
- Логи структурные (`structlog`), без паролей, токенов и ключей.
- Новые метрики регистрировать в `app/observability.py`.
- SQL только параметризованный, никаких f-строк в запросах.
- Тесты AI-слоя не требуют БД и сети — держать это свойство, CI быстрый.
- Комментарии писать только там, где неочевидно «почему»; «что» видно из кода.

## Режимы LLM

`LLM_MODE=mock` — полностью офлайн: `MockProvider` + `HashingEmbedder`. Семантический
кэш и RAG работают, пороги автоматически берутся из `*_LOCAL` (шкала у хэш-эмбеддера
ниже: парафраз ≈ 0.60, нерелевантное ≈ 0.00).

`LLM_MODE=live` + `LLM_API_KEY` — реальный провайдер; пороги переключаются на основные
(0.92 / 0.5) автоматически через `settings.cache_threshold`.
